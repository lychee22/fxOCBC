# 001-微前端框架选型

日期：2026-11-17
状态：已采纳

## 背景

OneBank 基座平台需支持 5 个业务子应用独立开发/构建/部署、运行时动态接入（规划文档 §1）。需在主流微前端方案中选定框架，作为接入协议的技术底座。

## 备选方案对比

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| qiankun | 生态成熟、生命周期/沙箱/HTML Entry 开箱即用；官方 examples 丰富；社区资料多，银行类项目案例广泛 | 基于 single-spa，部分场景调试链路长；对非 webpack 应用需额外适配 |
| wujie | 无需改造成本低（iframe + proxy），样式隔离天然 | 通信模型较新、坑位文档相对少；团队经验不足 |
| micro-app | WebComponent 方案接入简单 | 历史较短，复杂场景（多层嵌套、样式）偶有问题 |
| 自研（single-spa 裸用） | 灵活度最高 | 沙箱/加载/预渲染全要自建，成本高、风险大 |

## 结论

选 **qiankun 2.x**。核心理由：

1. 官方 examples/main 即基座参考实现，与本项目"基座 + N 子应用"模型完全同构，改造成本最低；
2. HTML Entry + JS 沙箱 + 全局状态三件套开箱即用，直接满足接入协议 §3/§5；
3. 行内同类系统多，踩坑资料充足，团队招聘/交接成本低。

## 后果与约束

- 子应用打包必须满足 UMD + 生命周期导出（arch/子应用接入协议 §2/§3）；
- 基座锁 qiankun 2.x 主版本；升级 3.x 须新立 adr 并评估契约破坏性；
- 严禁在子应用内二次引 qiankun 或绕过沙箱直接操作 window 顶层全局。
